\section{Контейнер и виртуальная машина}

Виртуальная машина (ВМ) работает на виртуальном оборудовании, которое предоставляет гипервизор, и имеет собственное ядро гостевой ОС. Контейнеризация основана на другом принципе: изолируются один или несколько процессов, но их системные вызовы обслуживает общее ядро Linux хоста (рис.~\ref*{fig:vm-vs-ct}). Если контейнеры запущены внутри ВМ, общим для них является ядро её гостевой ОС.

Поскольку контейнеры используют общее ядро, при их запуске не требуется загружать отдельную операционную систему. Степень изоляции зависит от конфигурации ядра и среды запуска.

\section{Архитектура Docker}

Для изоляции процессов и управления их ресурсами Docker использует несколько механизмов Linux:
\begin{itemize}[nosep]
  \item Пространства имён (namespaces) задают, какие системные ресурсы видит процесс. Пространство имён PID изолирует идентификаторы процессов, \cmd{mount} определяет видимые точки монтирования, \cmd{net} изолирует сетевые интерфейсы и маршруты.
  \item Контрольные группы (cgroups) учитывают и ограничивают потребление ресурсов группами процессов (глава \nameref*{ch:23-docker-resources}).
  \item Права доступа и разделение привилегий (capabilities) ограничивают действия процесса. Фильтры \cmd{seccomp} ограничивают системные вызовы.
\end{itemize}

Управление данными механизмами выполняет Docker Engine, который предоставляет программный интерфейс (API) для работы с образами и контейнерами. В базовой конфигурации Docker под Linux клиент \cmd{docker} передаёт запрос демону \cmd{dockerd} через Unix-сокет, а демон поручает управление жизненным циклом контейнера компоненту \cmd{containerd}. При запуске \cmd{containerd} использует промежуточный процесс shim, который вызывает \cmd{runc}. Среда выполнения \cmd{runc} настраивает изоляцию и запускает процесс контейнера согласно спецификации OCI (Open Container Initiative).

Образ содержит слои файловой системы и параметры запуска приложения. На его основе Docker формирует конфигурацию контейнера и добавляет записываемый слой. После создания контейнер можно многократно запускать и останавливать.

\section{Жизненный цикл контейнера}

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Для изучения жизненного цикла контейнера воспользуемся командами Docker. Сначала проверьте доступ к установленному Docker Engine:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
docker version
docker info
\end{minted}
\end{minipage}\par\addvspace{10pt}

Учитывайте, что в стандартной установке членство в группе \cmd{docker} позволяет управлять привилегированным демоном и фактически предоставляет полномочия, сопоставимые с правами \cmd{root}.

В командах ниже используются имена \cmd{course-box} и \cmd{course-web}. Если они уже заняты, выберите свободные и используйте их во всех командах.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
docker run -d --name course-box debian:12-slim sleep 600
docker ps
docker exec -it course-box bash
\end{minted}
\end{minipage}\par\addvspace{10pt}

Первая команда создаёт и запускает контейнер, в котором программа \cmd{sleep} работает 600 секунд. Если образ отсутствует локально, Docker предварительно загружает его. Если контейнер уже остановился, запустите его снова командой \cmd{docker start course-box}. Вторая команда показывает работающие контейнеры, а третья запускает дополнительную оболочку внутри контейнера.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}В оболочке контейнера выполните:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
cat /etc/os-release
tr '\0' ' ' < /proc/1/cmdline
echo
touch /tmp/course-file
exit
\end{minted}
\end{minipage}\par\addvspace{10pt}

Работа оболочки внутри контейнера не определяет его жизненный цикл. В стандартной конфигурации основной процесс контейнера имеет PID 1 в собственном пространстве имён, а при его завершении контейнер останавливается. Для PID 1 действуют особые правила обработки сигналов, поэтому приложение должно корректно обрабатывать завершение и при необходимости получать статусы дочерних процессов. Выход из дополнительной оболочки, запущенной через \cmd{docker exec}, основной процесс не останавливает.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Проверим, сохраняется ли созданный файл после остановки и повторного запуска контейнера:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
docker stop course-box
docker ps -a
docker start course-box
docker exec course-box ls /tmp/course-file
docker stop course-box
docker rm course-box
\end{minted}
\end{minipage}\par\addvspace{10pt}

Созданный файл сохраняется, поскольку при повторном запуске используется тот же контейнер. Основные команды управления контейнерами:
\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\centering\small\begin{tabular}{@{}>{\raggedright\arraybackslash}p{.38\linewidth}>{\raggedright\arraybackslash}p{.56\linewidth}@{}}
\toprule
\textbf{Команда} & \textbf{Назначение} \\
\midrule
\cmd{docker run} & Создать и запустить новый контейнер \\
\cmd{docker start} & Запустить существующий остановленный контейнер \\
\cmd{docker restart} & Остановить и снова запустить тот же контейнер \\
\cmd{docker exec} & Выполнить команду в работающем контейнере \\
\cmd{docker ps -a} & Показать все контейнеры, включая остановленные \\
\cmd{docker logs} & Просмотреть доступные журналы контейнера \\
\cmd{docker inspect} & Посмотреть конфигурацию и состояние \\
\cmd{docker stop} & Остановить контейнер \\
\cmd{docker rm} & Удалить остановленный контейнер и его записываемый слой \\
\bottomrule\end{tabular}\end{minipage}\par\addvspace{10pt}

При остановке через \cmd{stop} основной процесс получает настроенный сигнал (обычно \cmd{SIGTERM}). Если процесс не завершится за отведённое время, Docker отправит \cmd{SIGKILL}.

\section{Образы и реестры}

Чтобы использовать один и тот же образ на разных машинах, его можно разместить в реестре, предназначенном для хранения и распространения образов. Пример публичного реестра: Docker Hub. В имени \cmd{debian:12-slim} часть \cmd{debian} обозначает репозиторий, а \cmd{12-slim} является тегом. Один тег со временем может указывать на разное содержимое. Для точной идентификации манифеста образа или индекса манифестов используют дайджест (digest), например ссылку с \cmd{@sha256:...}.

Для работы с образами используются следующие команды:
\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\centering\small\begin{tabular}{@{}>{\raggedright\arraybackslash}p{.38\linewidth}>{\raggedright\arraybackslash}p{.56\linewidth}@{}}
\toprule
\textbf{Команда} & \textbf{Назначение} \\
\midrule
\cmd{docker pull debian:12-slim} & Загрузить образ из реестра \\
\cmd{docker image ls} & Показать локальные образы \\
\cmd{docker image inspect} & Посмотреть сведения об образе \\
\cmd{docker tag} & Добавить имя и тег для образа \\
\cmd{docker push} & Отправить образ в реестр при наличии необходимых прав \\
\cmd{docker image rm} & Удалить локальную ссылку или образ \\
\bottomrule\end{tabular}\end{minipage}\par\addvspace{10pt}

\section{Сеть и публикация портов}

Сетевая изоляция контейнера позволяет приложению использовать собственные сетевые интерфейсы и порты. В стандартной bridge-сети контейнер имеет отдельное сетевое пространство имён, сетевой интерфейс и IP-адрес. Пара виртуальных интерфейсов соединяет контейнер с программным мостом хоста. Адрес \cmd{localhost} внутри контейнера относится к его собственному сетевому пространству. Для доступа к приложению через порт хоста этот порт можно опубликовать при запуске контейнера.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
docker run -d --name course-web \
    -p 127.0.0.1:8080:80 nginx:1.30
curl --fail --retry 5 --retry-all-errors http://127.0.0.1:8080/
docker logs course-web
docker stop course-web
docker rm course-web
\end{minted}
\end{minipage}\par\addvspace{10pt}

Запросы к порту 8080 ВМ перенаправляются на порт 80 контейнера. Начиная с Docker Engine 28.0.0, в стандартной bridge-сети указание \cmd{127.0.0.1} ограничивает доступ к опубликованному порту самим хостом. Если порт 8080 занят, укажите свободный порт хоста в параметре \cmd{-p} и в команде \cmd{curl}.

\section{Типичные ошибки}
\begin{itemize}[nosep]
  \item Нет доступа к Docker: проверьте \cmd{docker version}, активный контекст и права. Не открывайте сокет всем пользователям.
  \item Контейнер сразу остановился: проверьте \cmd{docker ps -a}, \cmd{docker logs} и \cmd{docker inspect}. Одноразовая команда может завершиться штатно.
  \item Порт недоступен: проверьте публикацию, адрес прослушивания приложения и состояние контейнера.
  \item Данные исчезли после пересоздания: используйте внешнее хранилище (глава \nameref*{ch:21-docker-data}).
\end{itemize}
