\section{Зачем нужна непрерывная интеграция}

Перед коммитом легко забыть \cmd{make test}. В команде у каждого своё
окружение и набор зависимостей. При \textbf{непрерывной интеграции}
(Continuous Integration, CI) команда часто объединяет небольшие изменения
в общей ветке и автоматически проверяет сборку и тесты. Описание конвейера
хранится рядом с кодом и проходит ревью вместе с ним.

CI не доказывает, что программа идеальна. Он отвечает на конкретный вопрос:
можно ли воспроизвести сборку и проходят ли записанные проверки именно для
этого коммита? Поэтому ошибка превращается в короткий цикл:

\section{От ночных сборок к быстрой обратной связи}

Команды часто долго работали с отдельными копиями кода, а объединяли их
накануне релиза. Сборку запускали вручную или по расписанию ночью. Утром
оставалось разбирать длинный лог и искать, кто и какое изменение сломал.
Чем дольше изменения жили отдельно, тем дороже становилось их слияние:
конфликты, неявные зависимости и ошибки окружения накапливались вместе.

Ответом стала простая инженерная идея: если интеграция болезненна, делать её
нужно чаще и маленькими порциями. Проверку запускают сразу после отправки
изменений. Автор ещё помнит, что поменял, и может быстро найти причину сбоя.
Короткое время от изменения до понятного результата называют быстрой
обратной связью (\emph{fast feedback}).

Второй урок истории --- не доверять уникальной «машине для сборки», которую
кто-то когда-то настроил вручную. Такой сервер называют \emph{snowflake}:
он работает, но его трудно воспроизвести, заменить и объяснить. Современный
подход хранит описание сборки в репозитории (\emph{pipeline as code}) и
запускает её на чистом или одноразовом runner. Тогда команда проверяет не
«собралось ли у Пети», а «собирается ли проект по правилам, записанным в
репозитории».

Наконец, CI/CD --- это не только конфигурация. Это договор команды:
основная ветка должна оставаться рабочей, красный конвейер чинят в
приоритете, а тесты не удаляют ради формального успеха. Учебный сценарий
Mission Control специально воспроизводит этот договор в безопасном масштабе:
сначала намеренный инцидент, затем диагноз, исправление и только после этого
публикация результата.

\section{CI, Delivery и Deployment}

\begin{itemize}
  \item \textbf{CI} автоматически собирает и проверяет изменение, чтобы
    известная ошибка не дошла до основной ветки.
  \item \textbf{Continuous Delivery} (непрерывная поставка) поддерживает
    проверенную версию в состоянии готовности к выпуску. Команда решает,
    когда её выпускать.
  \item \textbf{Continuous Deployment} (непрерывное развёртывание)
    автоматически публикует прошедшую проверки версию в рабочей среде.
\end{itemize}

На учебном практикуме граница безопасна: успешный \cmd{main} публикует
статическую страницу GitHub Pages, а pull request только проверяется.

\section{Ветка, pull request и красный CI}

В \cmd{main} команда поддерживает рабочую версию. Изменение готовят в
отдельной ветке и открывают pull request (PR) --- запрос на слияние.
Перед слиянием изучают изменения и результат CI. На GitHub команда может
сделать проверку обязательной в настройках защиты ветки. Тогда GitHub
потребует, чтобы она прошла, прежде чем разрешить слияние.

\begin{warnbox}
Не удаляйте тест и не расширяйте допустимый диапазон только ради зелёной
галочки. Откройте первый упавший шаг, прочитайте его лог и исправьте
причину отдельным коммитом.
\end{warnbox}

Такой порядок сохраняет рабочий \cmd{main}, показывает, какой коммит внёс
проблему, и позволяет до merge прочитать diff. Даже в одиночном проекте это
полезная привычка.

\section{Из чего состоит workflow GitHub Actions}

GitHub Actions читает YAML-файлы из \fpath{.github/workflows/}.

\begin{center}
\begin{tabular}{@{}p{0.23\linewidth}p{0.66\linewidth}@{}}
\toprule
\textbf{Термин} & \textbf{Смысл} \\
\midrule
workflow & весь конвейер, описанный YAML-файлом \\
event / trigger & событие: \cmd{push}, \cmd{pull_request}, ручной запуск \\
job & задание на отдельном runner; jobs могут идти параллельно \\
step & последовательный шаг внутри job: \cmd{run} или \cmd{uses} \\
runner & временная машина, на которой исполняется job \\
artifact & файл или набор файлов, сохранённый после job \\
environment & именованная среда деплоя с правилами доступа \\
\bottomrule
\end{tabular}
\end{center}

Шаги внутри одного job идут последовательно. Jobs не обязаны ждать друг
друга: зависимость задаётся через \cmd{needs}.

\subsection{Триггеры и чистый runner}

\begin{minted}[bgcolor=gray!6]{yaml}
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  verify:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v6
      - name: Check the Make version
        run: make --version
\end{minted}

\cmd{pull_request} проверяет изменение до слияния, а \cmd{push} в \cmd{main}
проверяет принятую версию и может запускать деплой. Без
\cmd{actions/checkout} runner не увидит исходники и Makefile. Новая машина
не знает ничего о ваших локальных файлах, поэтому команды должны работать
из чистого клона, как описано в Makefile (\nameref{ch:14-make}).

\cmd{ubuntu-24.04} задаёт версию Ubuntu. GitHub обновляет пакеты в этом
образе, поэтому важные для проекта зависимости нужно задавать явно.

\section{Практический конвейер: Mission Control}

На семинаре вы соберёте Mission Control --- статическую панель миссии
с позывным из Evil Corp. В шаблоне есть программа на C с модульными
тестами, файл телеметрии \fpath{data/mission.env} и скрипты сборки.
Вы допишете два шага в задание \cmd{verify}. Каждый начинается с
\cmd{- name:}, а \cmd{run:} задаёт команду, как в примере выше.
Шаги проверок должны выполниться перед сборкой страницы.

\begin{minted}[bgcolor=gray!6]{yaml}
jobs:
  verify:
    runs-on: ubuntu-24.04
    steps:
      - name: Checkout code
        uses: actions/checkout@v6
      # Здесь добавьте шаги тестирования и проверки телеметрии.
      - name: Build Mission Control page
        run: make site report
      - name: Upload mission report
        uses: actions/upload-artifact@v4
        with:
          name: mission-report
          path: |
            artifacts/
            site/
\end{minted}

\cmd{make test} проверяет поведение функции. \cmd{make check-data} проверяет
конкретную конфигурацию миссии: например, кислород должен лежать в диапазоне
19--25 процентов. \cmd{make site report} создаёт HTML и текстовый отчёт.
\cmd{upload-artifact} прикрепляет результат к \emph{этому} запуску.

Если в PR стоит \cmd{OXYGEN=120}, модульные тесты по-прежнему проходят:
программа верно распознаёт недопустимое значение в тестовом примере.
Проверка конкретного файла телеметрии завершится ошибкой. Исправьте
значение в файле и сохраните прежние правила проверки.

\subsection{Граничные случаи}

Если допустим диапазон 19--25, тестируют не только «середину», но и границы:

\begin{center}
\begin{tabular}{@{}ccc@{}}
\toprule
Кислород & Ожидаемый результат & Причина \\
\midrule
18 & \cmd{NO-GO} & непосредственно ниже диапазона \\
19 & \cmd{GO} & нижняя допустимая граница \\
25 & \cmd{GO} & верхняя допустимая граница \\
26 & \cmd{NO-GO} & непосредственно выше диапазона \\
\bottomrule
\end{tabular}
\end{center}

Граничные тесты фиксируют договорённость о поведении. Если позже
\cmd{<=} случайно заменят на \cmd{<}, CI покажет регрессию.

\section{Как читать красный запуск}

Во вкладке \emph{Actions} выберите нужный run и найдите \textbf{первый}
упавший step: последующие часто пропущены лишь как следствие. Затем:

\begin{enumerate}
  \item прочитайте название шага, команду, код возврата и последние строки
    лога;
  \item воспроизведите ту же команду локально;
  \item исправьте причину отдельным коммитом;
  \item дождитесь зелёного run и только затем делайте merge.
\end{enumerate}

Страница запуска показывает, какой коммит проверялся и в каком шаге
произошёл сбой. В описании учебного PR сохраните ссылки на оба запуска и
объясните ошибку своими словами. В успешном запуске после слияния в
разделе \emph{Artifacts} можно скачать результат сборки.

\section{Артефакт, кэш и деплой}

\begin{center}
\begin{tabular}{@{}p{0.2\linewidth}p{0.31\linewidth}p{0.36\linewidth}@{}}
\toprule
 & \textbf{Для чего} & \textbf{Пример} \\
\midrule
Артефакт & сохранить результат конкретного run & бинарник, отчёт, готовый HTML \\
Кэш & ускорить запуск; потеря не влияет на корректность & пакеты, объектные
  файлы, данные \cmd{ccache} \\
Деплой & сделать проверенный результат доступным & GitHub Pages, staging \\
\bottomrule
\end{tabular}
\end{center}

Артефакт \cmd{mission-report} относится к конкретному запуску. Его можно
скачать, пока действует срок хранения. Другое задание может скачать его
в том же запуске. Кэш ускоряет повторную работу, а при его отсутствии
сборка заново создаёт те же результаты.

\section{Условный деплой на GitHub Pages}

Незавершённый PR не должен заменять рабочую страницу. Deploy зависит от
проверки и запускается только для push в \cmd{main}:

\begin{minted}[bgcolor=gray!6]{yaml}
  deploy:
    needs: verify
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
\end{minted}

\cmd{needs: verify} не позволяет deploy стартовать, пока проверка не
успешна. В отдельном job нужно скачать уже проверенный artifact и передать
сайт Pages:

\begin{minted}[bgcolor=gray!6]{yaml}
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: mission-report
          path: release
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v4
        with:
          path: release/site
      - id: deployment
        uses: actions/deploy-pages@v4
\end{minted}

До первого \cmd{push} с файлом workflow выберите
\emph{Settings $\to$ Pages $\to$ Source: GitHub Actions}. После успешной
публикации откройте панель по адресу из задания \cmd{deploy}. С панели
можно перейти к запуску с артефактом и к PR с историей исправления.
Для сдачи семинара достаточно отправить адрес этой панели.
Серверу или Docker-приложению потребуются также переменные окружения,
мониторинг и план отката (\nameref{ch:19-docker-basics},
\nameref{ch:22-docker-compose}).

\section{Происхождение результата и безопасность}

Отчёт и панель содержат хеш коммита (\cmd{GITHUB_SHA}) и номер запуска
(\cmd{GITHUB_RUN_NUMBER}). Сверьте их после публикации. Ссылка с панели
использует идентификатор запуска \cmd{GITHUB_RUN_ID}. В PR GitHub обычно
проверяет пробное слияние, а результат для сдачи берут из запуска по
\cmd{push} в \cmd{main}. Та же идея маркировки применяется к Docker-образам:

\begin{minted}[bgcolor=gray!6]{bash}
docker build -t registry.example.com/course/app:${GITHUB_SHA::7} .
docker push registry.example.com/course/app:${GITHUB_SHA::7}
\end{minted}

Тег \cmd{latest} не отвечает на вопрос, какой код развёрнут. Хеш коммита
позволяет найти исходники и откатиться на известную версию.

Workflow выполняет команды из репозитория, включая Makefile и тесты. Поэтому:

\begin{itemize}
  \item не храните пароли, токены и приватные ключи в репозитории;
  \item не печатайте секреты через \cmd{echo}, \cmd{env} или \cmd{set -x};
  \item для проверки кода из PR используйте \cmd{pull_request} и
    держите секреты вне задания проверки;
  \item выдавайте job только нужные права: job проверки не нужны права
    публикации Pages;
  \item не запускайте код чужих PR на своём runner с SSH-ключами или
    доступом к университетской инфраструктуре.
\end{itemize}

\section{Связь с остальным курсом}

Конвейер не добавляет магии. Он повторяет то, что вы делаете руками:
\cmd{make} (\nameref{ch:14-make}), тесты
(\nameref{ch:15-testing-optimization}), сценарии оболочки
(\nameref{ch:27-scripting-ide}), Git (\nameref{ch:25-git}) и при
необходимости Docker (\nameref{ch:19-docker-basics}). Сначала добейтесь,
чтобы проект собирался, проверялся и создавал результат локально; затем
переносите эти команды в CI.

\section{Задачи для самопроверки}
\begin{enumerate}
  \item Почему CI не гарантирует отсутствия всех ошибок?
  \item Чем step отличается от job? Когда нужен \cmd{needs}?
  \item Почему PR проверяется, но не должен деплоиться?
  \item Почему \cmd{OXYGEN=120} ломает проверку данных, хотя unit-тест
    функции может быть зелёным?
  \item Чем artifact отличается от кэша и от GitHub Pages?
  \item Какие условия не позволяют deploy опубликовать результат PR?
  \item Почему опасно давать секреты workflow, который исполняет код
    непроверенного PR?
  \item Как по странице и artifact найти коммит, из которого они собраны?
\end{enumerate}
