\chapter[CI/CD в GitHub Actions]{Непрерывная интеграция и публикация в GitHub Actions}
\label{ch:26-ci}

Предположим, два студента работают над одной программой на C. Один добавил аргумент к функции и исправил все известные ему места её вызова. Второй в это время написал новую проверку, в которой передал той же функции прежнее число аргументов. У каждого своя версия программы собиралась. После объединения изменений компилятор обнаружил вызов с неверным числом аргументов. Чтобы найти такую ошибку, нужно собрать и проверить общую версию проекта.

\section{От ночной сборки к проверке каждого изменения}

В Git историю проекта хранят в \textbf{репозитории}. \textbf{Коммит} фиксирует состояние файлов проекта. \textbf{Ветка} позволяет продолжать работу от выбранного коммита. Разработчики могут вести работу в собственных ветках, а затем переносить проверенные изменения в основную ветку проекта.

Объединение независимо подготовленных изменений называется \textbf{интеграцией}. Если выполнять её только перед выпуском программы, причину ошибки приходится искать среди множества правок. Одним из способов сократить этот промежуток стали ночные сборки. Ночью по расписанию запускалась сборка общей версии. Если утром сборка оказывалась неудачной, разработчики проверяли изменения за прошедший день.

В 1990-х годах Кент Бек описал \textbf{непрерывную интеграцию} (\emph{Continuous Integration}, CI) как одну из практик экстремального программирования — подхода к разработке небольшими, часто проверяемыми изменениями. Разработчики регулярно включают свою работу в общую ветку. Каждое объединение сопровождается автоматической сборкой и проверками. Если проверка обнаружила ошибку, автор может воспроизвести её, пока ещё помнит внесённые изменения. В примере с функцией достаточно сопоставить новое объявление с вызовом, на который указал компилятор. \href{https://martinfowler.com/articles/originalContinuousIntegration.html}{Мартин Фаулер и Мэттью Фоеммел. Continuous Integration}

Чтобы сборку мог повторить другой разработчик, её команды хранят рядом с исходным текстом. Например, в файле \texttt{Makefile} записывают, как собрать программу и запустить тесты. Если библиотека установлена только на компьютере автора, проверка на отдельной машине выявит пропущенную зависимость. Тогда автор сможет указать в проекте, какая библиотека требуется и как её установить.

\section{Что происходит после успешной проверки}

Сочетание \textbf{CI/CD} объединяет проверку изменений и подготовку версии к выпуску. У сокращения CD есть две распространённые расшифровки.

Непрерывная интеграция (\emph{Continuous Integration}) & Изменения регулярно объединяют в общей ветке. Команда получает результат автоматических проверок. & Проект собирается, тесты проходят после очередного изменения. \\
Непрерывная поставка (\emph{Continuous Delivery}) & Проверенная версия готова к выпуску. Момент выпуска выбирает человек. & Пакет собран и доступен для установки. Ответственный за выпуск может подтвердить публикацию. \\
Непрерывное развёртывание (\emph{Continuous Deployment}) & Каждая версия, прошедшая предусмотренные проверки в основной ветке, автоматически становится доступна пользователям. & После успешной проверки новой версии обновляется учебный сайт. \\

Далее мы рассмотрим проект семинара 7 — панель Mission Control. Это страница с показаниями приборов, названием миссии и позывным участника. Показания хранятся в текстовом файле \texttt{data/mission.env}. В учебном примере программу проверяют до объединения изменений, а сайт обновляют после успешной проверки основной ветки.

\section{Как прочитать описание проверки в GitHub Actions}

\textbf{GitHub Actions} — сервис GitHub, который может выполнить команды для определённой версии репозитория. Правила запуска и последовательность действий называются \textbf{рабочим процессом} (\emph{workflow}). Это описание хранится в каталоге \texttt{.github/workflows/} в файле формата \textbf{YAML}. В YAML вложенность записей обозначается отступами из пробелов. Дефис в начале записи обозначает элемент списка.

Ниже приведён самостоятельный пример для чтения. Если сохранить его отдельным файлом в указанном каталоге проекта Mission Control, он соберёт программу при отправке изменений в ветку \texttt{main}. В материалах семинара уже есть более полный файл \texttt{ci.yml}, с которым вы будете работать на занятии.

\begin{minted}[bgcolor=gray!6]{yaml}
name: Сборка программы
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - name: Получить файлы проекта
        uses: actions/checkout@v6
      - name: Собрать программу
        run: make all
\end{minted}

Прочитайте этот пример в порядке выполнения:

\begin{enumerate}
\item Запись \texttt{on} указывает \textbf{событие}, при котором GitHub запускает работу. Событие \texttt{push} происходит при отправке изменений в репозиторий. Здесь выбрана только ветка \texttt{main}. Поле \texttt{name} в первой строке задаёт название, которое появится во вкладке \textbf{Actions}.
\item В разделе \texttt{jobs} описаны \textbf{задания} (\emph{jobs}). Здесь одно задание с именем \texttt{build}. Для него GitHub выделяет \textbf{исполнителя} (\emph{runner}) — программу, которая выполнит шаги задания на выделенной машине. Значение \texttt{ubuntu-24.04} выбирает предоставленную GitHub машину с Ubuntu. Запись \texttt{contents: read} разрешает читать содержимое репозитория.
\item Раздел \texttt{steps} задаёт последовательность \textbf{шагов} внутри задания. Первый шаг получает файлы проекта. Поле \texttt{uses} указывает готовое действие (\emph{action}), а \texttt{@v6} — выбранную версию этого действия. До получения файлов в рабочем каталоге исполнителя ещё нет исходного текста программы.
\item Второй шаг вызывает \texttt{make all}. Поле \texttt{run} задаёт команду оболочки, а \texttt{name} — подпись шага в журнале. Слово \texttt{all} обозначает \textbf{цель} — именованное правило в \texttt{Makefile}. В этом проекте оно собирает программу \texttt{build/mission-control}. Оба шага работают с одним каталогом, поэтому второй видит файлы, полученные первым.
\end{enumerate}

Ту же сборку можно повторить в терминале. Перейдите в корневой каталог проекта, где лежит \texttt{Makefile}, и выполните команды по очереди:

\begin{minted}[bgcolor=gray!6]{bash}
make all
./build/mission-control 21 42
\end{minted}

Первый аргумент программы задаёт содержание кислорода в процентах, второй — температуру реактора в градусах Цельсия. При этих значениях ожидается строка \texttt{oxygen=21\% reactor=42C mission=GO}. Так можно проверить, что программа, которую предстоит собирать автоматически, запускается и на вашей машине.

\section{Две проверки одного проекта}

В Mission Control есть два независимых вопроса. Правильно ли программа оценивает переданные ей показания? И допустимы ли показания, записанные в файле для публикации? Для ответов нужны разные проверки.

\begin{longtable}{>{\raggedright\arraybackslash}p{\dimexpr 0.29\linewidth-2\tabcolsep\relax}>{\raggedright\arraybackslash}p{\dimexpr 0.39\linewidth-2\tabcolsep\relax}>{\raggedright\arraybackslash}p{\dimexpr 0.32\linewidth-2\tabcolsep\relax}}
\toprule
Команда из корневого каталога проекта & Что проверяется & При каком результате проверка успешна \\
\midrule
\endhead
\texttt{make test} & \textbf{Модульные тесты} вызывают отдельную функцию программы с заранее заданными значениями и сравнивают ответ с ожидаемым. & Для каждого набора аргументов получен ожидаемый ответ, в том числе отказ \texttt{NO-GO} при опасных показаниях. \\
\texttt{make check-data} & Проверяются значения в файле \texttt{data/mission.env}, из которого будут построены страница и отчёт. & Кислород находится в диапазоне от 19 до 25 процентов, а температура — от \(-20\) до 60 градусов включительно. \\
\bottomrule
\end{longtable}

Например, в модульном тесте допустимо передать функции значение кислорода 120 и ожидать отказа. Правильный отказ означает, что тест пройден. То же число в \textbf{файле данных} означает, что публиковать показание нельзя. На семинаре вы самостоятельно запишете обе команды отдельными шагами. У каждого появится своё название в журнале, поэтому при сбое будет видно, какая именно проверка обнаружила проблему.

\section{Где искать причину сбоя}

Для обсуждения изменений на GitHub открывают \textbf{запрос на слияние} (\emph{pull request}, PR) из рабочей ветки в основную. В файле семинара, помимо \texttt{push} для \texttt{main}, указано событие \texttt{pull\_request} для запросов в \texttt{main}. GitHub запускает проверку при открытии такого запроса и при добавлении в него очередного коммита. Обычно при этом проверяется результат пробного объединения веток.

Предположим, в запросе на слияние изменили строку на \texttt{OXYGEN=120}. Как восстановить ход проверки?

\begin{enumerate}
\item Откройте вкладку \textbf{Actions} в репозитории. Выберите запуск \textbf{Mission Control}, относящийся к вашему PR, затем задание \texttt{verify}. В нём видны шаги в порядке выполнения.
\item Откройте первый шаг с отметкой ошибки. В \textbf{журнале} — записи команд и напечатанных ими сообщений — найдите строку \texttt{Unsafe mission: OXYGEN=120, expected 19..25}. Она указывает фактическое значение и допустимый диапазон.
\item Программа сообщает оболочке результат работы числом — \textbf{кодом завершения}. Ноль означает успешное выполнение. Здесь проверка данных вернула ненулевой код, поэтому шаг завершился ошибкой. При обычных настройках следующие шаги этого задания пропускаются. Общее сообщение о ненулевом коде указывает на сбой, а строка выше объясняет его причину.
\item В собственной копии той же ветки выполните \texttt{make check-data}. Сопоставьте вывод с журналом. После исправления файла отправьте новый коммит в ту же ветку. У PR появится новый запуск, а журнал предыдущего останется доступен для сравнения.
\end{enumerate}

\section{Что именно публикуется}

\textbf{Артефакт} (\emph{artifact}) — сохранённый результат конкретного запуска. В проекте семинара задание \texttt{verify} после проверок создаёт страницу и текстовый отчёт, затем сохраняет их вместе с программой как артефакт \texttt{mission-report}. Его можно скачать на странице запуска в разделе \textbf{Artifacts}. Чтобы ускорить будущие запуски, можно использовать \textbf{кэш} — хранилище файлов, которые пригодятся повторно, например загруженных библиотек. Для проверки результата по конкретной версии нужен артефакт.

\textbf{GitHub Pages} — служба публикации сайтов из готовых файлов. До первой отправки рабочего процесса выберите \textbf{Settings \(\to\) Pages \(\to\) Build and deployment \(\to\) Source \(\to\) GitHub Actions}. В файле семинара за публикацию отвечает отдельное задание \texttt{deploy}. Следующие строки взяты из его описания:

\begin{minted}[bgcolor=gray!6]{yaml}
deploy:
  needs: verify
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
\end{minted}

Запись \texttt{needs: verify} задаёт зависимость: публикация может начаться после успешного завершения задания \texttt{verify}. Условие \texttt{if} ограничивает публикацию событием отправки изменений в основную ветку. Здесь \texttt{github.event\_name} — имя события, \texttt{github.ref} — полное обозначение ветки или другой ссылки Git, а \texttt{\&\&} требует выполнения обоих условий. Разбор двух случаев показывает, зачем нужны обе записи:

\begin{minted}[bgcolor=gray!6]{text}
Запрос на слияние в main → проверка и, при успехе, артефакт → сайт сохраняет прежнюю версию
Отправка в main          → проверка и, при успехе, артефакт → публикация файлов из артефакта
\end{minted}

Задания выполняются на отдельных машинах GitHub. Поэтому \texttt{deploy} скачивает сохранённые файлы и передаёт каталог сайта в GitHub Pages. Так на сайт попадают файлы, которые подготовило задание проверки. Право публикации требуется только заданию \texttt{deploy}. Пароли и личные ключи для этих команд в файлы проекта записывать не требуется.

После слияния откройте запуск для \texttt{main}, затем опубликованную страницу. На панели указаны позывной, номер запуска и \textbf{идентификатор коммита} (SHA) — строка, по которой можно найти точную версию проекта. Перейдите с панели к запуску, скачайте \texttt{mission-report} и откройте файл \texttt{mission-report.txt} из архива. Сверьте значение \texttt{commit} с идентификатором на странице. По ссылке на PR можно восстановить, какое значение потребовало исправления. Для сдачи семинара передайте преподавателю адрес опубликованной панели.

\section{Самопроверка}

\begin{enumerate}
\item При сборке на новой машине компилятор сообщил, что не нашёл библиотеку. Какую информацию автору нужно добавить в проект, чтобы сборку мог повторить другой разработчик?
\item У функции появился новый аргумент, но один тест вызывает её по старым правилам. На каком этапе вы ожидаете ошибку — при сборке тестовой программы или при сравнении её ответа с ожидаемым?
\item В запросе на слияние все проверки прошли, артефакт можно скачать, а опубликованный сайт показывает прежнее значение. Объясните это по двум строкам описания задания \texttt{deploy}.
\item Вам дали адрес панели. Как по нему установить, к какому коммиту относится отчёт и какая проверка обнаружила исходную ошибку?
\end{enumerate}
