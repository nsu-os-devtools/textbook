\section{Зачем процессам общаться}

У каждого процесса, как правило, собственное виртуальное адресное пространство и таблица файловых дескрипторов. Для обмена данными и согласования действий используются механизмы межпроцессного взаимодействия (IPC). Механизмы IPC рассмотрим на примере Linux, а практические задания выполним в терминале своей ВМ.

\section{Файлы}

Для обмена данными между процессами можно использовать общий файл, в который один процесс записывает данные, а другой их читает. Такой способ удобен, когда данные необходимо сохранить для последующего чтения, в том числе после завершения процессов.

Если несколько процессов обращаются к файлу одновременно, они могут согласовывать операции чтения и записи с помощью файловых блокировок. Чтобы не опрашивать файл постоянно, читающий процесс может получать уведомления ядра Linux о его изменениях через механизм \cmd{inotify}. Для передачи потока данных без промежуточного хранения в файле используют каналы.

\section{Каналы (pipe)}

Канал передаёт поток байтов в одном направлении через буфер ядра (рис.~\ref*{fig:ipc-pipe}). В случае успеха вызов \cmd{pipe()} записывает в переданный массив два файловых дескриптора: \cmd{fd[0]} для чтения и \cmd{fd[1]} для записи. Дескрипторы разных процессов могут указывать на один канал: например, после \cmd{fork()} дочерний процесс наследует оба дескриптора.

    \draw[flow] (b) -- (r);
  \end{tikzpicture}
  \caption{Передача данных через канал.}
  \label{fig:ipc-pipe}
\end{figure}

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Оболочка создаёт такие каналы при построении конвейера:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
printf 'one\ntwo\n' | wc -l
\end{minted}
\end{minipage}\par\addvspace{10pt}

В данном примере оболочка соединяет стандартный вывод первой команды со стандартным вводом второй, поэтому \cmd{wc -l} получает две строки и выводит число 2.

Канал передаёт непрерывный поток байтов без границ отдельных операций записи. При блокирующем вводе-выводе чтение из пустого канала ожидает поступления данных, пока открыт хотя бы один дескриптор записи. Если буфер заполнен, запись ожидает освобождения места.

Закрытие дескрипторов позволяет процессам определить, что обмен завершён. Когда закрыты все дескрипторы записи и буфер опустел, \cmd{read()} возвращает 0, обозначая конец потока. Если же закрыты все дескрипторы чтения, попытка записи вызывает сигнал \cmd{SIGPIPE}. При блокировании или игнорировании этого сигнала, а также при возврате из его обработчика вызов \cmd{write()} завершается с ошибкой \cmd{EPIPE}.

\subsection{Пример на C}

В примере ниже родительский процесс передаёт дочернему один байт, а оба процесса закрывают ненужные им концы канала: родитель закрывает дескриптор чтения, а дочерний процесс закрывает дескриптор записи.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Сохраните код в файле \file{pipe-demo.c}:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,fontsize=\footnotesize]{c}
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int fd[2], status;
    if (pipe(fd) == -1) return EXIT_FAILURE;
    pid_t pid = fork();
    if (pid == -1) return EXIT_FAILURE;
    if (pid == 0) {
        char c;
        close(fd[1]);
        if (read(fd[0], &c, 1) != 1) _exit(1);
        close(fd[0]);
        _exit(write(STDOUT_FILENO, &c, 1) != 1);
    }
    close(fd[0]);
    ssize_t n = write(fd[1], "A", 1);
    close(fd[1]);
    if (waitpid(pid, &status, 0) == -1) return EXIT_FAILURE;
    putchar('\n');
    return n == 1 && WIFEXITED(status) && WEXITSTATUS(status) == 0
        ? EXIT_SUCCESS : EXIT_FAILURE;
}
\end{minted}
\end{minipage}\par\addvspace{10pt}

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Скомпилируйте и запустите программу:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
gcc -Wall -Wextra -o pipe-demo pipe-demo.c
./pipe-demo
\end{minted}
\end{minipage}\par\addvspace{10pt}

Программа выводит букву A. Вызов \cmd{waitpid()} позволяет родительскому процессу дождаться завершения дочернего. При передаче произвольных объёмов данных необходимо учитывать частичное чтение и запись, ошибки и прерывания системных вызовов.

\subsection{Именованный канал (FIFO)}

В отличие от анонимного канала, именованный канал (FIFO) доступен по имени в файловой системе. Это позволяет организовать обмен между независимыми процессами, если у них есть необходимые права. Как и в анонимном канале, данные передаются через буфер ядра и не сохраняются в файле на диске.

При открытии FIFO в блокирующем режиме процесс обычно ожидает, пока другой процесс откроет противоположный конец канала. Чтобы увидеть это на практике, создайте FIFO и начните чтение в первом терминале. Если имя занято, выберите свободное и используйте его в обоих терминалах.
\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
mkfifo -m 600 ~/course-fifo && cat ~/course-fifo
\end{minted}
\end{minipage}\par\addvspace{10pt}
\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Во втором терминале той же ВМ выполните:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
printf 'hello\n' > ~/course-fifo
\end{minted}
\end{minipage}\par\addvspace{10pt}
После открытия канала на запись в первом терминале появится строка \cmd{hello}, а после закрытия дескриптора записи команда \cmd{cat} завершится.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Удалите созданный канал:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
rm ~/course-fifo
\end{minted}
\end{minipage}\par\addvspace{10pt}


\section{Сокеты}

Сокет представляет собой конечную точку обмена данными, доступную процессу в Linux через файловый дескриптор. В отличие от канала, сокеты позволяют организовать обмен не только внутри одной системы, но и по сети. Способ адресации задаётся семейством адресов, а модель передачи данных определяется типом сокета:

\begin{itemize}[nosep]
  \item \cmd{AF_UNIX}: Unix-сокеты для локального взаимодействия, в том числе через имена в файловой системе. Так клиент Docker может обращаться к демону.
  \item \cmd{AF_INET} и \cmd{AF_INET6}: взаимодействие через IP, как между процессами одной машины, так и по сети.
  \item \cmd{SOCK_STREAM}: упорядоченный поток байтов, например TCP. Границы сообщений задаёт приложение.
  \item \cmd{SOCK_DGRAM}: отдельные сообщения (датаграммы), например UDP. Свойства доставки зависят от протокола.
\end{itemize}

При установлении соединения через потоковый сокет сервер обычно выполняет \cmd{socket()}, \cmd{bind()} и \cmd{listen()}, а клиент использует \cmd{socket()} и \cmd{connect()}. Вызов \cmd{accept()} возвращает серверу отдельный дескриптор для обмена с клиентом. Исходный сокет остаётся в режиме прослушивания и используется для приёма новых подключений.

\section{Общая память}

Общая память представляет собой область памяти, доступную нескольким процессам. Каждый из них отображает один и тот же объект в собственное виртуальное адресное пространство, поэтому для обмена данными не требуется отдельно копировать их через канал. При одновременном изменении общей переменной результат может зависеть от порядка выполнения операций. Такое явление называют состоянием гонки. Для согласования доступа используют семафоры или мьютексы, настроенные для межпроцессного использования, поскольку сама общая память не обеспечивает синхронизацию.

Для работы с именованным объектом общей памяти POSIX вызов \cmd{shm_open()} открывает или создаёт объект, \cmd{ftruncate()} задаёт размер нового объекта, а \cmd{mmap()} с флагом \cmd{MAP_SHARED} создаёт отображение. По окончании работы процессы удаляют свои отображения вызовом \cmd{munmap()}, а имя объекта удаляют через \cmd{shm_unlink()}.

\section{Очереди сообщений и сигналы}

Очередь сообщений представляет собой механизм IPC, при котором отправитель помещает отдельные сообщения в очередь, а получатель извлекает их. В очередях POSIX каждому сообщению назначается приоритет. Для открытия очереди используют \cmd{mq_open()}, для отправки сообщения \cmd{mq_send()}, а для получения \cmd{mq_receive()}. В первую очередь извлекаются сообщения с более высоким приоритетом. При равном приоритете действует порядок поступления. Если очередь заполнена, блокирующая операция отправки ожидает освобождения места.

Сигнал представляет собой асинхронное уведомление процесса о событии. Например, \cmd{SIGTERM} обычно используют для запроса завершения процесса. В Linux несколько ожидающих экземпляров обычного сигнала одного номера объединяются в один. Сигналы реального времени помещаются в очередь и могут передавать значение, заданное при вызове \cmd{sigqueue()}.

\section{Типичные ошибки}
\begin{itemize}[nosep]
  \item Читатель канала не завершается: проверьте, закрыты ли все дескрипторы записи, включая унаследованные.
  \item FIFO ожидает бесконечно: проверьте наличие процесса, открывающего противоположный конец.
  \item Повреждение общих данных: проверьте синхронизацию всех обращений.
  \item Отказ при подключении к сокету: проверьте адрес, наличие слушателя и права доступа.
\end{itemize}
