\section{Сборка образа}

Dockerfile задаёт инструкции сборки образа и параметры запуска контейнера. В современных версиях Docker Engine сборку Linux-образов по умолчанию выполняет BuildKit (рис.~\ref*{fig:docker-build}). Последний аргумент команды \cmd{docker build} задаёт контекст сборки, из которого \cmd{COPY} получает локальные файлы. Точка (\cmd{.}) обозначает текущий каталог.

\section{Основные инструкции}

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\centering
\small
\begin{tabular}{@{}lp{.72\linewidth}@{}}
\toprule
\textbf{Инструкция} & \textbf{Назначение} \\
\midrule
\cmd{FROM} & Выбор базового образа и начало этапа сборки \\
\cmd{WORKDIR} & Рабочий каталог последующих инструкций и запуска \\
\cmd{RUN} & Выполнение команды при сборке \\
\cmd{COPY} & Копирование файлов из контекста или другого этапа \\
\cmd{ADD} & Копирование с дополнительными возможностями \\
\cmd{ARG} & Параметр сборки \\
\cmd{ENV} & Переменная окружения для сборки и запуска \\
\cmd{LABEL} & Метаданные образа \\
\cmd{USER} & Пользователь для последующих команд и запуска \\
\cmd{EXPOSE} & Описание порта приложения без публикации \\
\cmd{ENTRYPOINT} & Основная команда запуска контейнера \\
\cmd{CMD} & Команда или аргументы по умолчанию \\
\bottomrule
\end{tabular}
\end{minipage}\par\addvspace{10pt}

Если необходимо только скопировать файлы из контекста сборки, используют \cmd{COPY}. Инструкция \cmd{ADD} дополнительно поддерживает автоматическую распаковку локальных архивов tar и загрузку удалённых файлов.

При настройке приложения следует учитывать, что значения \cmd{ARG} и \cmd{ENV} могут сохраняться в метаданных образа или истории сборки, поэтому для передачи секретов следует использовать специальные возможности BuildKit, например \cmd{RUN --mount=type=secret}.

\section{Команда запуска}

Инструкции \cmd{RUN}, \cmd{CMD} и \cmd{ENTRYPOINT} различаются назначением и поддерживают две формы записи: через оболочку и в виде массива JSON. Например, в Linux команда \cmd{RUN make} по умолчанию выполняется через \cmd{/bin/sh -c}, тогда как \cmd{RUN ["make"]} запускает программу непосредственно. Во втором случае подстановки оболочки недоступны без её явного запуска.

Инструкция \cmd{RUN} выполняется при сборке образа, а \cmd{CMD} и \cmd{ENTRYPOINT} определяют поведение контейнера при запуске. Если обе инструкции записаны в форме JSON, \cmd{ENTRYPOINT} задаёт основную команду, а \cmd{CMD} её аргументы по умолчанию.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Например:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{Dockerfile}
FROM debian:12-slim
ENTRYPOINT ["/bin/echo"]
CMD ["hello"]
\end{minted}
\end{minipage}\par\addvspace{10pt}
При запуске без дополнительных аргументов контейнер выведет \cmd{hello}. Аргументы, указанные после имени образа в команде \cmd{docker run}, заменяют \cmd{CMD}. Параметр \cmd{--entrypoint} позволяет изменить саму точку входа. Форма непосредственного запуска не создаёт дополнительную оболочку, которая могла бы помешать доставке сигналов основному приложению.

\section{Слои и кэш}

Образ состоит из слоёв файловой системы и метаданных. Инструкции \cmd{RUN} и \cmd{COPY} могут создавать новые слои, тогда как \cmd{CMD} и \cmd{LABEL} изменяют только метаданные.

BuildKit повторно использует сохранённые результаты операций, если их входные данные не изменились. При изменении содержимого копируемого файла результат соответствующей операции и зависимых от неё операций необходимо получить заново. Изменение содержимого удалённого репозитория пакетов само по себе не приводит к сбросу кэша \cmd{RUN}. Поэтому зависимости устанавливают до копирования часто изменяемого исходного кода, а обновление списка пакетов и их установку выполняют в одной инструкции \cmd{RUN}.

Порядок инструкций влияет не только на скорость сборки, но и на размер образа. Если временные файлы создаются и удаляются в одной инструкции \cmd{RUN}, они не попадают в итоговый слой этой операции. Удаление файлов в следующем слое скрывает их из файловой системы образа, но они продолжают занимать место в предыдущем слое.

\section{Практика: многоступенчатая сборка}

Многоступенчатая сборка позволяет разделить среду компиляции программы и среду её выполнения. Рассмотрим данный подход на примере программы на C. Создайте пустой каталог \file{course-build} и разместите в нём три файла.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Файл \file{main.c}:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,fontsize=\footnotesize]{c}
#include <stdio.h>

int main(void) {
    puts("answer: 42");
    return 0;
}
\end{minted}
\end{minipage}\par\addvspace{10pt}

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Файл \file{Makefile}:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,fontsize=\footnotesize]{Makefile}
CC = gcc
CFLAGS = -Wall -Wextra -O2
app: main.c
    $(CC) $(CFLAGS) -o app main.c
\end{minted}
\end{minipage}\par\addvspace{10pt}
\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Файл \file{Dockerfile}:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{Dockerfile}
FROM debian:12-slim AS build
RUN apt-get update && apt-get install -y \
    --no-install-recommends gcc make libc6-dev && rm -rf \
    /var/lib/apt/lists/*
WORKDIR /src
COPY main.c Makefile ./
RUN make

FROM debian:12-slim
COPY --from=build /src/app /usr/local/bin/app
USER 65534:65534
CMD ["/usr/local/bin/app"]
\end{minted}
\end{minipage}\par\addvspace{10pt}

\par\pagebreak[4]
На первом этапе устанавливаются инструменты компиляции и создаётся исполняемый файл. На второй этап переносится только собранная программа, поэтому компилятор и промежуточные файлы не входят в конечный образ. Для запуска динамически скомпонованной программы необходимы совместимые загрузчик и библиотеки. Использование одной базовой системы на обоих этапах упрощает соблюдение этого условия.

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Из каталога с файлами выполните:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
docker build -t course-c:1.0 .
docker run --rm course-c:1.0
docker image history course-c:1.0
\end{minted}
\end{minipage}\par\addvspace{10pt}

При запуске программа должна вывести \cmd{answer: 42}. Чтобы проследить работу кэша, измените строку в \file{main.c}, повторите сборку и проверьте вывод. При неизменных зависимостях BuildKit может повторно использовать результаты предыдущих операций.

Для сборки необходим доступ к репозиториям образов и пакетов. Поскольку тег базового образа может быть переназначен, а версии пакетов не зафиксированы, побайтовая воспроизводимость не гарантируется. После работы удалите учебный образ:
\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\begin{minted}[bgcolor=gray!6,breaklines=false,fontsize=\footnotesize]{bash}
docker image rm course-c:1.0
\end{minted}
\end{minipage}\par\addvspace{10pt}

\section{Файл .dockerignore}

\par\addvspace{10pt}\noindent\begin{minipage}{\linewidth}
\setlength{\parindent}{0pt}\noindent\hspace*{1.25cm}Файл \file{.dockerignore} находится в корне контекста сборки и исключает из него ненужные файлы. Для данного примера достаточно:\par\kern 10pt
\begin{minted}[bgcolor=gray!6,fontsize=\footnotesize]{text}
.git
*.o
app
.env
\end{minted}
\end{minipage}\par\nobreak\addvspace{10pt}\nobreak

В результате служебные файлы и результаты локальной компиляции не попадут в контекст сборки, что уменьшит его объём.

\par\pagebreak[4]
\section{Типичные ошибки}
\begin{itemize}[nosep]
  \item \cmd{COPY} не находит файл: проверьте контекст сборки и \file{.dockerignore}.
  \item \cmd{make} не находит цель: проверьте наличие Makefile, рабочий каталог и табуляцию.
  \item Образ слишком велик: перенесите инструменты сборки в отдельный этап, удаляйте временные данные в той же инструкции.
  \item Программа не запускается: проверьте архитектуру, права и наличие динамических библиотек в конечном образе.
  \item Изменение портов через \cmd{EXPOSE} не открыло доступ: опубликуйте нужный порт при запуске.
\end{itemize}
