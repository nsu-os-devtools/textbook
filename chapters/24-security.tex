\chapter{Основы безопасности}
\label{ch:24-security}

При подключении по SSH сервер проверяет, кто запрашивает вход.
Это \textbf{аутентификация}. Затем для каждого запроса система
решает, разрешена ли операция. Это \textbf{авторизация}.

\section{Принцип минимальных привилегий}

Служба сбора показаний отправляет измерения в базу данных. Для этой
задачи достаточно разрешить ей добавлять записи в одну таблицу.
Если в программе окажется ошибка, выданные полномочия определят её
последствия: служба сможет отправить неверное измерение, но попытку
удалить таблицу база отклонит. Выбор полномочий по набору необходимых
операций называют \textbf{принципом минимальных привилегий}.

\section{Политики безопасности процессов}

На учебной ВМ программа может получить отказ при операции, разрешённой
обычными правами доступа (глава~\ref{ch:05-permissions}).
В этом случае стоит выяснить, действует ли для программы дополнительная
политика ядра. Рассмотрим, как найти причину отказа в двух таких системах.

\subsection{AppArmor: профиль программы}

На Ubuntu можно ограничить действия службы с помощью \textbf{профиля
AppArmor}. Профиль задаёт, например, какие файлы служба может открыть
для чтения и куда может писать. Поэтому один и тот же файл может
открываться из терминала и оставаться недоступным для службы.
Файлы профилей обычно находятся в \fpath{/etc/apparmor.d/}.

Рассмотрим службу сбора показаний. Чтение её файла настроек
разрешает следующее правило профиля:

\begin{minted}[bgcolor=gray!6]{text}
/etc/sensors/service.conf r,
\end{minted}

Буква \cmd{r} разрешает чтение по указанному пути. Администратор перенёс
конфигурацию в \fpath{/srv/sensors/service.conf} и поменял путь в
настройках запуска. При следующем запуске служба сообщает
\emph{Permission denied}. Чтобы проверить, связан ли отказ с AppArmor,
на ВМ с Ubuntu выполните:

\begin{minted}[bgcolor=gray!6]{bash}
sudo aa-status
sudo journalctl -k -b --since '10 min ago' | grep 'apparmor="DENIED"'
\end{minted}

Первая команда показывает загруженные профили и их режимы.
В режиме \emph{enforce} ядро применяет правила профиля. Режим
\emph{complain} помогает при его настройке: обращения, для которых
не хватает разрешающего правила, обычно допускаются и записываются
в журнал. Вторая команда ищет отказы среди недавних сообщений ядра
за текущую загрузку. Вот существенные поля одной учебной записи:

\begin{minted}[bgcolor=gray!6]{text}
apparmor="DENIED" operation="open" profile="sensor-reader"
name="/srv/sensors/service.conf" requested_mask="r" denied_mask="r"
\end{minted}

В поле \cmd{profile} указан профиль службы, в \cmd{name} --- путь,
который она действительно открывала. Значение \cmd{denied_mask="r"}
объясняет, какую операцию заблокировали. Сопоставив путь с правилом
выше, можно обнаружить расхождение. Если перенос был случайным,
верните файл и настройку запуска к исходному пути. Если новый путь
выбран намеренно, администратор уточняет правило в профиле и загружает
обновлённый профиль. После этого повторите запуск и проверьте, смогла
ли служба прочитать настройки. Подробности приведены в
\href{https://ubuntu.com/server/docs/how-to/security/apparmor/}{руководстве Ubuntu по AppArmor}.

\subsection{SELinux: метки и типы}

На Fedora и в системах семейства Red Hat можно встретить
\textbf{SELinux}. Здесь при проверке доступа важны метки процесса и
файла. Например, политика для веб-сервера разрешает процессу с типом
\cmd{httpd_t} читать статические страницы с типом \cmd{httpd_sys_content_t}.
Если страницу переместили из домашнего каталога, файл может сохранить
прежнюю метку. Тогда сервер вернёт ошибку доступа, хотя страница лежит
по ожидаемому пути.

На ВМ с SELinux и установленным веб-сервером проверьте режим защиты и
метку существующей страницы:

\begin{minted}[bgcolor=gray!6]{bash}
getenforce                          # режим защиты
ls -Z /var/www/html/index.html      # текущая метка файла
matchpathcon /var/www/html/index.html   # ожидаемая метка для пути
\end{minted}

В режиме \emph{Enforcing} SELinux блокирует запрещённые действия.
В режиме \emph{Permissive} регистрирует их и допускает выполнение,
а \emph{Disabled} означает, что SELinux выключен. Команды относятся
к ВМ с этим механизмом защиты и соответствующими утилитами.

Метка состоит из нескольких полей, разделённых двоеточиями.
Например, в записи \cmd{unconfined_u:object_r:user_home_t:s0}
третье поле \cmd{user_home_t} обозначает тип содержимого домашнего
каталога. Если для страницы в \fpath{/var/www/html} команда
\cmd{matchpathcon} показывает тип \cmd{httpd_sys_content_t}, сравнение
даёт конкретную причину проверить журнал аудита:

\begin{minted}[bgcolor=gray!6]{bash}
sudo ausearch -m AVC -ts recent     # недавние решения о доступе в журнале аудита
\end{minted}

В записи об отказе \cmd{avc: denied} поле \cmd{scontext} показывает
контекст процесса, \cmd{tcontext} --- объекта. Сверьте время и имя
файла с неудавшимся запросом. Для стандартного каталога сайта
администратор может восстановить метку, предусмотренную политикой:

\begin{minted}[bgcolor=gray!6]{bash}
restorecon -nv /var/www/html/index.html       # предварительный просмотр
sudo restorecon -v /var/www/html/index.html   # применить к одной странице
ls -Z /var/www/html/index.html                # проверить результат
\end{minted}

После исправления повторите запрос страницы. Если тип уже соответствовал
ожидаемому, повторная установка метки ничего не исправит: продолжите
поиск по журналам SELinux и самого веб-сервера.
См. \href{https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/using_selinux/troubleshooting-problems-related-to-selinux_using-selinux}{руководство Red Hat по диагностике SELinux}.

\section{Доступ по SSH}

Когда вы вводите \cmd{ssh login@pglab.nsu.ru}, на вашем компьютере
работает \textbf{клиент} SSH, а на удалённой машине --- \textbf{сервер}
SSH. При входе по ключу участвуют две независимые \textbf{ключевые пары}.
В каждой паре есть закрытый ключ, которым владелец создаёт цифровую
подпись, и открытый ключ, которым другая сторона проверяет эту подпись.
Открытый ключ можно передавать, закрытый остаётся у владельца.

\begin{itemize}
  \item \textbf{Пара сервера (ключи хоста).} Закрытый ключ хранится на
    сервере. Благодаря открытому ключу ваш клиент может убедиться, что
    подключился именно к учебной машине.
  \item \textbf{Пара пользователя.} Вы создаёте её на своём компьютере
    и передаёте на сервер открытый ключ. По нему сервер сможет проверить,
    что запрос на вход подписан вашим закрытым ключом.
\end{itemize}

Создание пары и установка открытого ключа описаны в
главе~\ref{ch:02-linux-access}. Посмотрим, что происходит при
подключении, когда ключ пользователя уже установлен.

\subsection{Как клиент проверяет ключ хоста}

При первом подключении к машине клиент ещё не знает, какой открытый
ключ принадлежит этому хосту. Например, при входе на учебную машину
с условным именем \cmd{vm-demo} OpenSSH может показать:

\begin{minted}[bgcolor=gray!6,fontsize=\footnotesize]{text}
ED25519 key fingerprint is SHA256:BKDDO8by8GL8d1r7OSjUDqDMmmE6Es6Xh5J2DBpAQy8.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
\end{minted}

Строка от \cmd{SHA256:} до точки --- \textbf{отпечаток} открытого ключа
хоста. Клиент вычисляет его из полученного ключа с помощью хеш-функции
SHA-256. Один и тот же ключ всегда даёт один и тот же отпечаток.
Поэтому преподаватель может узнать отпечаток непосредственно в консоли
ВМ и показать его студентам на занятии. Для ключа хоста Ed25519 команда
и её вывод в нашем примере выглядят так:

\begin{minted}[bgcolor=gray!6]{bash}
ssh-keygen -l -E sha256 -f /etc/ssh/ssh_host_ed25519_key.pub
\end{minted}
\begin{minted}[bgcolor=gray!6,fontsize=\footnotesize]{text}
256 SHA256:BKDDO8by8GL8d1r7OSjUDqDMmmE6Es6Xh5J2DBpAQy8 vm-demo (ED25519)
\end{minted}

Сравните отпечаток из приглашения SSH с полученным от преподавателя
для вашей ВМ. Если он целиком совпал, введите \cmd{yes}. Клиент сохранит
имя хоста и его открытый ключ в \fpath{~/.ssh/known_hosts}. Теперь при
новом подключении SSH может проверить ключ автоматически. При расхождении
остановитесь и уточните отпечаток: показанный выше относится только
к примеру.

\subsection{Как подпись подтверждает владение закрытым ключом}

Открытый ключ хоста может скопировать кто угодно. Откуда клиент знает,
что собеседнику доступен и закрытый ключ? Для этого SSH проверяет
\textbf{подпись текущего обмена} (рис.~\ref{fig:security-ssh-keys}).

\begin{figure}[!htb]
  \centering
  \begin{tikzpicture}[font=\small]
    \node[process] (c) at (0,0) {Клиент SSH};
    \node[process] (h) at (8.8,0) {Сервер SSH};
    \draw[dashed] (c.south) -- (0,-5);
    \draw[dashed] (h.south) -- (8.8,-5);
    \draw[flow] (8.8,-1) -- node[above]{Ключ хоста и подпись при обмене ключами} (0,-1);
    \node[anchor=west,font=\small\itshape] at (0,-1.45) {Клиент проверяет подлинность хоста};
    \draw[flow] (0,-2.4) -- node[above]{Имя пользователя, открытый ключ и подпись} (8.8,-2.4);
    \node[anchor=east,font=\small\itshape] at (8.8,-2.9) {Сервер проверяет разрешение и подпись};
    \draw[flow] (8.8,-3.8) -- node[above]{Подтверждение входа} (0,-3.8);
    \draw[bidir] (0,-4.7) -- node[above]{Команды и вывод в защищённом канале} (8.8,-4.7);
  \end{tikzpicture}
  \caption{Вход по SSH с ключом пользователя. Время идёт сверху вниз.
    После проверки хоста аутентификация пользователя уже проходит
    по зашифрованному соединению.}
  \label{fig:security-ssh-keys}
\end{figure}

\begin{enumerate}
  \item В начале подключения клиент и сервер обмениваются свежими
    данными для согласования сеансовых ключей. Каждый у себя вычисляет
    хеш обмена --- значение, которое зависит от данных обеих сторон
    и полученного ими общего секрета.
  \item Сервер подписывает этот хеш своим закрытым ключом хоста
    и посылает клиенту подпись вместе с открытым ключом.
  \item Клиент берёт три величины: хеш, который он вычислил сам,
    полученную подпись и проверенный открытый ключ хоста. Алгоритм
    проверки подтверждает, что подпись для этого хеша создана
    соответствующим закрытым ключом. В следующем сеансе данные обмена
    будут другими, поэтому запись старой подписи проверку не пройдёт.
\end{enumerate}

Таким образом, отпечаток позволяет человеку узнать постоянный ключ ВМ,
а подпись позволяет программе проверить собеседника при каждом
подключении. Для шифрования команд и вывода SSH использует сеансовые
ключи, полученные во время обмена.

\subsection{Как сервер проверяет пользователя}

Теперь по защищённому каналу клиент запрашивает вход под именем
\cmd{login}. На этот раз подписывает клиент: он использует закрытый
ключ пользователя и подписывает идентификатор текущего сеанса вместе
с данными запроса, включая имя учётной записи. Сервер проверяет
подпись открытым ключом пользователя и проверяет, разрешён ли этот
ключ для входа под именем \cmd{login}. Обычно разрешённые открытые
ключи перечислены в \fpath{~/.ssh/authorized_keys} в домашнем каталоге
этой учётной записи. Если проверки прошли и дополнительных способов
подтверждения не требуется, сервер разрешает вход. Закрытый ключ
пользователя всё это время остаётся на его компьютере.

\subsection{Типичные ошибки подключения}

\noindent\textbf{Ключ хоста изменился.}
Если SSH сообщает, что ключ хоста изменился, уточните новый отпечаток
у администратора до продолжения работы. Это бывает после переустановки
ВМ, но такое же сообщение появится при подключении к другому серверу
под прежним именем.

\begin{itemize}
  \item Сообщение \emph{Permission denied (publickey)} означает, что
    сервер не принял вход по ключу. Сверьте имя пользователя, открытый
    ключ в его \fpath{authorized_keys} и выбранный на клиенте ключ.
    Флаг \cmd{-v} у \cmd{ssh} показывает, какие ключи клиент предлагает.
  \item Сообщение \emph{UNPROTECTED PRIVATE KEY FILE} относится к файлу
    на клиенте: OpenSSH отказывается использовать закрытый ключ, который
    доступен посторонним. Проверьте доступ к этому файлу по
    главе~\ref{ch:05-permissions}.
  \item Если кому-либо отправлен закрытый ключ, создайте новую пару,
    настройте вход с ней и отзовите старый ключ на всех серверах, где
    он был разрешён. Удаление копии из переписки не отзывает доступ.
\end{itemize}

\subsection{Вход по ключу и отключение входа по паролю}

Успешный вход по ключу означает, что сервер принял ключ. Он всё ещё
может предлагать пароль другим клиентам. Разберём настройку отдельной
ВМ с Ubuntu, где администратор хочет разрешить SSH-вход по ключу.
Настройки общего сервера курса меняет его администратор.

Сначала откройте второй терминал на своём компьютере. Попросите клиент
использовать для проверки только вход по ключу. Например, для хоста
\cmd{myvm}, настроенного в главе~\ref{ch:02-linux-access}, команда такая:

\begin{minted}[bgcolor=gray!6]{bash}
ssh -S none -o PreferredAuthentications=publickey myvm
\end{minted}

Если сервер
отклонит ключ, клиент завершит попытку. Запрос парольной фразы от
закрытого ключа относится к файлу на вашем компьютере.
Оставьте исходный сеанс открытым до окончания проверки.

На Ubuntu проверьте основной файл \fpath{/etc/ssh/sshd_config}.
В типовой конфигурации директива \cmd{Include} подключает каталог
с дополнительными настройками. Для отдельной ВМ администратор может
создать там новый файл командой:

\begin{minted}[bgcolor=gray!6]{bash}
sudoedit /etc/ssh/sshd_config.d/00-course-access.conf
\end{minted}

Допустим, по SSH на эту ВМ должны входить только Анна и администратор.
Тогда содержимое файла может выглядеть так:

\begin{minted}[bgcolor=gray!6]{text}
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
AllowUsers anna labadmin
\end{minted}

Первая строка разрешает аутентификацию открытым ключом. Вторая отключает
метод \emph{password}. Третья отключает интерактивные запросы сервера:
через них PAM тоже может запрашивать пароль. Если на машине таким
способом запрашивают второй фактор, для неё нужна другая конфигурация.
В последней строке укажите настоящие имена всех необходимых учётных
записей, включая ту, из которой администрируете ВМ.

Перед применением проверьте синтаксис и прочитанные значения. Для
большинства параметров OpenSSH использует первое подходящее значение,
поэтому важен порядок включения файлов. Пример ниже предполагает общие
правила без условных блоков \cmd{Match}:

\begin{minted}[bgcolor=gray!6]{bash}
sudo sshd -t
sudo sshd -T | grep -E 'authentication |^allowusers '
\end{minted}

При успешной проверке \cmd{sshd -t} обычно ничего не выводит.
Сверьте вывод второй команды с выбранными правилами. Только после
этого выполните на Ubuntu \cmd{sudo systemctl reload ssh}.
Откройте новое подключение с ноутбука и проверьте вход по ключу.
Повторите команду из второго терминала: параметр \cmd{-S none}
заставляет клиент открыть отдельное сетевое соединение.
Если вход отклонён, используйте прежний сеанс, чтобы исправить список
или отменить изменения в добавленном файле, снова проверить конфигурацию
и перечитать её. Параметры описаны в \cmd{man 5 sshd_config} и в
\href{https://ubuntu.com/server/docs/how-to/security/openssh-server/}{руководстве Ubuntu по OpenSSH}.

\subsection{Fail2ban: временная блокировка после повторных отказов}

Запись \emph{Failed password} в журнале SSH означает, что одна попытка
входа завершилась отказом. Если с одного адреса за короткое время
приходит много таких сообщений, Fail2ban может временно заблокировать
подключения с этого адреса. Настройка для одной службы называется
\emph{jail}: она связывает источник событий, фильтр и действие при
достижении порога.

Например, в секции \cmd{[sshd]} можно задать \cmd{maxretry = 5},
\cmd{findtime = 10m} и \cmd{bantime = 15m}. Тогда пять подходящих под
фильтр отказов с одного адреса за десять минут приведут к блокировке
на пятнадцать минут. Посмотреть уже имеющиеся события на Ubuntu и
состояние установленного Fail2ban можно так:

\begin{minted}[bgcolor=gray!6]{bash}
sudo journalctl -u ssh --since '1 hour ago'
sudo fail2ban-client status         # список включённых jail
sudo fail2ban-client status sshd    # состояние jail для SSH
\end{minted}

В выводе для \cmd{sshd} поле \emph{Currently banned} показывает число
действующих блокировок, а \emph{Banned IP list} --- сами адреса.
Если \cmd{sshd} отсутствует в списке jail, установленный Fail2ban
не выполняет эту проверку для SSH. См. \cmd{man jail.conf}.

\section{Хранение секретов}

\subsection{Что даёт токен доступа}

\textbf{Токен доступа} (access token) --- значение, которое система
выдаёт клиенту для обращения к определённому ресурсу. Например, студент
разрешает системе сборки скачать образ из закрытого реестра. Реестр
выдаёт токен с правом чтения образов учебного проекта на один час.
Сборка предъявляет токен при запросе. Реестр проверяет его действительность,
срок и разрешённое действие. С тем же токеном запрос на публикацию
нового образа будет отклонён.

Для HTTP API распространён тип \emph{bearer}: предъявителю достаточно
знать само значение. Поэтому даже короткоживущий токен передают по HTTPS.
Так выглядит заголовок запроса с вымышленным значением:

\begin{minted}[bgcolor=gray!6]{text}
Authorization: Bearer demo-example-only
\end{minted}

Второй пример --- служба записи показаний датчиков. Ей нужен токен
с правом добавлять измерения в одну базу. Человек, скопировавший такой
bearer-токен, тоже сможет добавлять измерения до истечения срока или
отзыва доступа. Для каждой службы удобно выдавать отдельный токен:
по журналу понятно, чьи полномочия использовались, и замена значения
у одной службы не прервёт работу остальных.

\subsection{Передача секрета через файл или окружение}

Если программа получает токен из файла, храните его вне дерева проекта:
тогда токен не попадёт в репозиторий или образ контейнера при обычном
копировании исходного кода. Доступ к файлу настраивают при его создании
(глава~\ref{ch:05-permissions}).

Другой способ передачи токена --- \textbf{переменная окружения}.
Её может установить система запуска служб. При этом дочерние процессы
обычно наследуют окружение, а диагностический вывод \cmd{env} может
попасть в журнал вместе с токеном.

\subsection{Как служба получает секрет из Vault}

Предположим, службе сборки нужен токен для скачивания образов.
Реестр выдаёт токен с правом чтения одного проекта на час, а
администратор помещает его в хранилище секретов Vault. При запуске
происходят три действия:

\begin{enumerate}
  \item Сборочная служба подтверждает Vault свою учётную запись
    способом, настроенным для этой ВМ. Vault выдаёт ей собственный
    краткоживущий токен с разрешением читать нужную запись хранилища.
  \item Служба предъявляет этот токен Vault и получает из записи
    токен реестра. Именно токен реестра она отправляет при скачивании
    образа. В репозитории проекта достаточно хранить путь к записи.
  \item Когда токен Vault истечёт, для нового чтения понадобится снова
    пройти аутентификацию. Уже полученная копия токена реестра
    действует до срока, заданного самим реестром, или до отзыва в нём.
\end{enumerate}

Так можно заменить токен реестра в одном месте. Следующая сборка
получит обновлённое значение при чтении записи. Для приведённого
примера используется заранее сохранённый секрет. Подробнее о сроках
действия см. в \href{https://developer.hashicorp.com/vault/docs/concepts/tokens}{документации Vault}.

\subsection{Утечка и отзыв}

Если токен оказался в опубликованном коммите, считайте, что у него
могли появиться копии. Отзовите токен у выдавшей его системы,
настройте службу на новый и проверьте журнал использования старого.
Удаление строки в следующем коммите сохраняет её в истории Git.
По той же причине настоящий токен опасно вводить прямо в командной
строке или печатать в сообщении об ошибке.

\section{Сетевая изоляция: файрвол и группы безопасности}

\textbf{Файрвол} (англ.\ \emph{firewall}) проверяет
сетевые пакеты по заданным правилам и решает, какие из них пропустить,
а какие заблокировать. Например, на учебной ВМ работает веб-приложение.
Студентам нужно открывать его из лаборатории, а подключения из других
сетей следует блокировать. Для этого в правиле указывают, откуда пришёл пакет
(IP-адрес источника) и куда он направлен (протокол и порт назначения).

\subsection{Где применяются правила}

В Linux правила фильтрации можно задать средствами \textbf{nftables}.
В Ubuntu для типовых задач удобно использовать утилиту \cmd{ufw}.
Оба примера ниже относятся к файрволу внутри ВМ. В облаке есть ещё одно
место для проверки трафика --- \textbf{группа безопасности}. Это набор
правил, которые облачная платформа применяет к трафику ВМ на своей
стороне. Входящее подключение должно пройти обе проверки
(рис.~\ref{fig:security-firewall}).

Пусть приложение слушает TCP-порт 8080 на сетевом адресе ВМ.
В примере диапазон \cmd{192.0.2.0/24} обозначает учебную подсеть.
На своей ВМ подставьте диапазон, который сообщил администратор.

\begin{figure}[htb]
  \centering
  \begin{tikzpicture}[node distance=0.55cm]
    \node[process] (client) {Ноутбук в учебной сети};
    \node[process, below=of client] (cloud) {Группа безопасности в инфраструктуре};
    \node[process, below=of cloud] (vm) {Файрвол внутри ВМ};
    \node[process, below=of vm] (app) {Приложение слушает TCP-порт 8080};
    \draw[flow] (client) -- (cloud);
    \draw[flow] (cloud) -- (vm);
    \draw[flow] (vm) -- (app);
  \end{tikzpicture}
  \caption{Путь входящего подключения к облачной ВМ. Группа безопасности
    применяется, если её предоставляет инфраструктура.}
  \label{fig:security-firewall}
\end{figure}

Для входящего трафика в группе безопасности указывают источник
\cmd{192.0.2.0/24}, протокол TCP и порт назначения 8080. Проверьте,
нет ли другого правила, разрешающего тот же порт для более широкой
сети.

\subsection{Правило UFW для учебной подсети}

На Ubuntu с уже включённым UFW посмотрите действующие правила:
\cmd{sudo ufw status verbose}. Для примера предполагаем, что входящие
подключения по умолчанию запрещены, доступ по SSH уже разрешён,
а других правил для порта 8080 нет. Администратор добавляет разрешение
и проверяет результат:

\begin{minted}[bgcolor=gray!6]{bash}
sudo ufw allow in proto tcp from 192.0.2.0/24 to any port 8080
sudo ufw status numbered
\end{minted}

\cmd{in} задаёт входящее направление, \cmd{from} --- адреса источников,
\cmd{to any port 8080} --- порт назначения на ВМ. В списке правил
проверьте порт, действие \cmd{ALLOW IN} и подсеть. При статусе
\emph{inactive} UFW не фильтрует трафик. Перед его включением на
удалённой ВМ администратор должен разрешить доступ к фактическому
порту SSH из своей сети.

Проверьте результат с ноутбука в разрешённой подсети: откройте в
браузере адрес ВМ с портом 8080. Для HTTP-службы можно также выполнить
\cmd{curl -I http://192.0.2.10:8080/}, подставив адрес своей ВМ.
При проверке из другой маршрутизируемой подсети соединение должно
быть отклонено или завершиться по тайм-ауту. Для отмены своего правила
снова запросите список с номерами и выполните \cmd{sudo ufw delete N},
подставив текущий номер именно этой строки.
См. \href{https://ubuntu.com/server/docs/how-to/security/firewalls/}{руководство Ubuntu по UFW}.

\subsection{Как прочитать правило nftables}

Если фильтрацией на ВМ управляют напрямую через nftables, действующий
набор правил показывает \cmd{sudo nft list ruleset}. Найдите базовую
цепочку с \cmd{hook input}: через неё проходят пакеты, адресованные самой
ВМ. В такой цепочке разрешение из предыдущего примера может выглядеть так:

\begin{minted}[bgcolor=gray!6]{text}
ip saddr 192.0.2.0/24 tcp dport 8080 accept
\end{minted}

Здесь \cmd{ip saddr} проверяет IPv4-адрес источника, \cmd{tcp dport}
--- TCP-порт назначения, а \cmd{accept} разрешает подходящий пакет.
Чтобы понять результат для других адресов, прочитайте остальные правила
и политику цепочки. Например, при \cmd{policy drop} пакет, дошедший
до конца цепочки без разрешения, отбрасывается. Это пример чтения
конфигурации на машине с nftables; на ВМ под управлением UFW для
изменений достаточно команд UFW.

\subsection{Что именно слушает служба}

Чтобы принимать подключения по TCP, процесс создаёт сокет, связывает
его с локальным адресом и портом и начинает прослушивание. На ВМ
список таких сокетов можно посмотреть без изменения настроек сети:

\begin{minted}[bgcolor=gray!6]{bash}
ss -lnt                 # прослушиваемые TCP-сокеты, адреса и порты числами
\end{minted}

Посмотрите на столбец \emph{Local Address:Port}. Запись
\cmd{127.0.0.1:8080} означает, что служба принимает подключения через
петлевой интерфейс этой машины. Это подходит, например, для базы данных,
если приложение работает на той же ВМ. Запись \cmd{0.0.0.0:8080}
означает прослушивание на всех локальных IPv4-адресах. Для IPv6
петлевой адрес записывают как \cmd{::1}.

\subsection{Как читать вывод \cmd{ss}}

\begin{minted}[bgcolor=gray!6]{text}
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN 0      128        127.0.0.1:8080      0.0.0.0:*
LISTEN 0      128          0.0.0.0:22        0.0.0.0:*
\end{minted}

В этом примере первая служба принимает локальные подключения к порту
8080, а вторая слушает порт 22 на всех IPv4-адресах ВМ.
\cmd{0.0.0.0:*} в правом столбце означает, что у слушающего сокета
ещё нет конкретного собеседника. Адрес привязки читают в левом
столбце. В самой команде \cmd{-l} выбирает слушающие сокеты,
\cmd{-n} сохраняет числовые порты, \cmd{-t} выбирает TCP.
Команда \cmd{ss -lun} покажет UDP-сокеты, ожидающие датаграммы.
Добавьте \cmd{-p}, чтобы увидеть процесс, если хватает прав.

\subsection{Почему служба доступна на ВМ, но недоступна с ноутбука}

Предположим, что приложение должно отвечать по HTTP на порту 8080.
Проверки удобно расположить по пути подключения:
\begin{enumerate}
  \item На ВМ выполните \cmd{ss -lnt 'sport = :8080'}. Пустой список
    означает, что в этом сетевом пространстве сейчас нет слушающего
    TCP-сокета на порту 8080. Проверьте запуск службы и её журнал.
  \item Если указан адрес \cmd{127.0.0.1}, проверьте службу на самой ВМ
    командой \cmd{curl -I http://127.0.0.1:8080/}. Даже ответ HTTP 404
    подтверждает, что TCP-соединение состоялось и сервер обработал запрос.
    На ноутбуке адрес \cmd{127.0.0.1} ведёт на сам ноутбук.
  \item Если служба слушает адрес учебной сети, используйте на ноутбуке
    адрес ВМ и тот же порт. Проверьте подключение к VPN и правила
    фильтрации на пути. Тайм-аут сам по себе не указывает, какой именно
    узел потерял или отбросил пакеты.
\end{enumerate}
Для сервиса, предназначенного только для самой ВМ, привязка к петлевому
адресу соответствует задаче. Подробности о сокетах и выводе команд
см. в главе~\ref{ch:18-ipc} и в \cmd{man ss}.

\section{Обновления и зависимости}

Допустим, в библиотеке обнаружили уязвимость и разработчики выпустили
исправление. Перед обновлением нужно выяснить, какая версия содержит
патч и откуда получен файл для установки. После обновления стоит
проверить, какую копию библиотеки использует программа.

\subsection{Как проверить хеш скачанного файла}

При ручной загрузке архива с исходниками или установочного образа
сверьте его \textbf{хеш SHA-256} до распаковки или запуска. Это
контрольная сумма содержимого файла: утилита \cmd{sha256sum} читает
файл целиком и выводит 64 шестнадцатеричных знака. Если при загрузке
файл повредился или кто-то изменил его содержимое, сумма изменится.

Например, вы скачали ISO-образ Ubuntu с зеркала. На официальной странице
\emph{того же выпуска} доступны список сумм \fpath{SHA256SUMS} и его
подпись \fpath{SHA256SUMS.gpg}. Подготовьте ключ подписи образов по
\href{https://ubuntu.com/tutorials/how-to-verify-ubuntu}{инструкции Ubuntu}
и сверьте его отпечаток с опубликованным Ubuntu. Поместите образ и оба
файла в отдельный каталог, перейдите в него и выполните:

\begin{minted}[bgcolor=gray!6]{bash}
gpg --verify SHA256SUMS.gpg SHA256SUMS   # проверить подпись издателя
\end{minted}

Убедитесь, что подпись верна и принадлежит проверенному ключу Ubuntu.
Теперь сравните содержимое образа с подписанным списком:

\begin{minted}[bgcolor=gray!6]{bash}
sha256sum --check --ignore-missing SHA256SUMS
\end{minted}

В списке могут быть образы для нескольких архитектур. Параметр
\cmd{--ignore-missing} пропускает файлы, которых в каталоге нет.
Проверьте, что напротив \emph{имени вашего образа} стоит \cmd{OK}
(в русском переводе --- «ЦЕЛ»). Если утилита сообщает о несовпадении
или не нашла ни одного файла для проверки, отложите установку.
Сверьте имя файла, выпуск и архитектуру с официальной страницей,
при необходимости скачайте образ заново и повторите проверку.

Эталонная сумма важна не меньше самого файла. Если автор подменённого
архива положит рядом сумму своей копии, проверка тоже покажет \cmd{OK}.
Подпись списка позволяет установить, что эталонные суммы опубликовал
владелец доверенного ключа. При этом даже подлинный архив старой версии
может содержать известную уязвимость.

\subsection{Как узнать, установлен ли патч}

Для пакетов из настроенного репозитория эту проверку выполняет APT:
он проверяет подпись метаданных репозитория и по цепочке контрольных
сумм сверяет индекс пакетов и скачанный пакет. Подробнее см.
\cmd{man 8 apt-secure}. Если APT сообщает об ошибке подписи или
несовпадении суммы, проверьте источник и повторите загрузку из
доверенного репозитория.

В \href{https://ubuntu.com/security/notices}{бюллетене безопасности Ubuntu}
найдите свой выпуск системы, имя пакета и версию с исправлением.
Обновите список пакетов командой \cmd{sudo apt update} и сравните версию
из бюллетеня с установленной. Например, для сервера OpenSSH:

\begin{minted}[bgcolor=gray!6]{bash}
apt list --upgradable      # доступные обновления по локальному индексу
apt-cache policy openssh-server   # установленная и предлагаемая версии
\end{minted}

Для установки доступных обновлений администратор выполняет
\cmd{sudo apt upgrade}. Исправление может находиться в общей библиотеке,
которой пользуются сразу несколько программ. Если при обновлении файл
библиотеки заменили, уже запущенный процесс может продолжать использовать
старую копию, отображённую в его адресное пространство. Такую службу
нужно перезапустить, если этого ещё не сделала система обновления.

Если приложение поставляется со своей копией уязвимой библиотеки,
обновление системного пакета её не затронет. В этом случае установите
выпуск приложения с исправленной зависимостью. Для собственного проекта
обновите зависимость и пересоберите приложение.

\section{Типичные ошибки}
\begin{itemize}
  \item После переноса конфигурации служба получила отказ, и администратор
    отключил весь профиль AppArmor. Сопоставьте путь в сообщении об отказе
    с правилом профиля: часто достаточно исправить путь в настройках службы.
  \item Служба исправно отвечает на ВМ, но недоступна с соседней
    машины. Проверьте в \cmd{ss -lnt}, на каком адресе она слушает,
    затем проверьте маршрут и правила фильтрации.
  \item Записали хеш только что скачанного архива и сразу сверили архив
    с этой записью. Для проверки происхождения файла возьмите эталонную
    сумму из доверенного источника.
  \item После \cmd{apt update} считают уязвимость устранённой.
    Сверьте установленную версию пакета с версией, содержащей исправление.
\end{itemize}

\section{Связь с остальным курсом}

Безопасность входит в повседневную работу с учебной ВМ. При подключении
по SSH проверка ключа хоста помогает убедиться, что соединение установлено
с нужным сервером (\nameref{ch:02-linux-access}). Права на файлы определяют,
какие данные сможет прочитать или изменить запущенная программа
(\nameref{ch:05-permissions}). При установке программ APT проверяет
происхождение и целостность пакетов, а через обновления доставляет
исправления известных уязвимостей (\nameref{ch:08-packages}).

\section{Задачи для самопроверки}
\begin{enumerate}
  \item Служба записывает измерения в базу. Какие операции достаточно
    разрешить ей для этой задачи? Как ограничится ущерб при утечке токена?
  \item После переноса конфигурации служба получила отказ при чтении.
    Что проверит администратор в профиле AppArmor? Что он проверит
    в системе с SELinux?
  \item Где SSH хранит сведения о знакомых серверах, а где ---
    список ключей для входа в учётную запись? Кто проверяет каждый файл?
  \item Скопированы открытый ключ хоста и подпись из вчерашнего
    SSH-соединения. Почему отпечаток этого ключа сегодня будет тем же,
    а подпись для нового соединения не подойдёт?
  \item После изменения настроек SSH прежний сеанс продолжает работать.
    Как, сохраняя этот сеанс, проверить возможность нового входа?
  \item Истёк токен доступа сборочной службы к Vault. Что произойдёт с
    токеном реестра, который служба уже прочитала из хранилища?
  \item Из истории разработки токен попал в общий репозиторий.
    Что произойдёт с уже скопированным токеном после удаления файла?
    Как прекратить действие этого токена?
  \item Служба слушает \cmd{127.0.0.1:8080}. Администратор разрешил
    входящие подключения к порту 8080 в файрволе. Почему
    с соседней машины по-прежнему нельзя подключиться напрямую?
  \item На зеркале опубликованы образ и файл с его хешем. Проверка
    показала \cmd{OK}. Как проверить, что образ совпадает с выпущенным
    разработчиками? Где выяснить, входит ли в него нужное исправление?
  \item На диске установлена библиотека с исправлением. Почему
    администратору важно знать, какие процессы были запущены до обновления?
\end{enumerate}
